## Durable semantics
Request acceptance atomically captures a private SHA256 fingerprint of the server-read customer ID in its disabled task. Status responses never expose that fingerprint or raw billing ID. A duplicate request cannot rewrite it. A legacy task without an acceptance binding stays held; current profile data is not substituted as historical evidence.
The executor binds UID/revision/policy/acceptedAt/customer fingerprint, requires explicit server-side task activation inside an already-validated QA scope, and claims a sixty-second epoch lease. It pins the verified subscription inventory, rejects missing creation evidence or subscriptions created after acceptance, and requires the provider's current customer fingerprint to match the accepted one. Provider sole-ownership/account/mode checks remain in the Stripe adapter. A leased execution guard is rechecked immediately before the actual Stripe update, not only before a potentially slow lookup.
Each verified subscription has a hash-keyed receipt. Lost responses reuse deletion/uid/revision/subscription idempotency keys; already verified receipts are re-read from the provider before completion. Only validated transient network/server errors schedule bounded exponential retries, up to five attempts; unknown or ownership/inventory/receipt failures require review. Epoch/revision changes prevent stale results from updating a new request. Completing billing does not delete, freeze or restart an account. Cancelling an accepted deletion request does not restart a previously stopped renewal.
Completion writes task proof and the request's renewal status atomically, disables further execution, and preserves the original verification time on duplicate reads. Internal receipts are private workflow evidence, not a new public privacy promise. Production retention/disposal of workflow evidence, live ownership binding and operational ingress still need an exact-source activation review.
