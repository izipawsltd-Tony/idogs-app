# Scoped independent receipt publisher and restored-Auth quarantine — 30 October 2026

## Actual separate-database prototype

The new default-disabled component runs only with all approved demo-idogs-deletion emulators. It requires the source database to be (default), the receipt database to be the distinct local idogs-deletion-ledger-qa, an explicit synthetic UID/UUID nonce, and both SDK endpoints pinned to the current loopback emulator host/port with TLS disabled. It rejects cloud projects, the source database reused as the ledger, remote SDK endpoints and missing opt-in before IO. The named database exists only inside the local emulator; no cloud database, IAM/provider setting or resource was created.

For this one approved synthetic UID/revision1, acceptance publication reads the actual source request/policy/dates and captures their immutable commitment hash. Completion publication requires consistent completed request/job/lock/receipt and actual Auth absence. Receipt events use transactionally created deterministic IDs, predecessor hashes and a nonce-bound sequence/head. Duplicate/restarted publishers verify the exact receipt instead of rewriting it. Concurrent publishers must produce one event and a duplicate. Reads verify the bounded complete event chain and the head; erased heads, orphan events, replaced scope, altered content or revision fail closed. No collection-wide account scan occurs.

The receipt database is outside the default database's simulated restore boundary. A read before and after Auth inspection must have the same sequence/hash watermark. Missing history is a hold, not permission to write. Accepted/completed deletion receipts also hold; an enabled or disabled restored Auth identity is quarantined regardless of its historical identity attributes. This component does not issue a new-generation admission certificate or automatically release any tombstone.

The document adapter can explicitly receive this server-bound ledger guard. It checks the verified token UID against the ledger scope during each identity check before creating a session or writing. Existing ungated prototype behavior remains available only as the prior unwired component; no live route or Production mode was enabled. The new guard is deliberately unsuitable for admitting ordinary accounts: no history is held until a separate reviewed admission/current-history protocol exists.

## Explicit remaining gaps

This is a scoped current receipt protocol in an emulator, not a globally complete live ledger. Source request acceptance and independent publication are separate transactions. Intake does not yet atomically require external publication, and there is no continuous global reconciliation, cross-service atomicity, cloud durability/IAM proof or full-project-restore isolation. Reports retain sourcePublicationAtomic:false,globalCompletenessVerified:false,productionReady:false. A restored or erased external ledger never grants access; its authority/freshness and operational admission still need reviewed integration. Hash chaining does not establish resistance to a privileged rewrite of the entire independent store.

No completed managed workflow was dispatched, no original seven-day fixture was changed and no message/simulation was sent. Historical artifact verification remains separate and historicalOnly:true. Next work is guarded intake publication intent/ack/reconciliation and restore-generation admission, followed by signed authority drain/resolvers and the no-send post-Auth outbox.
