## Deletion model coverage gaps discovered in the actual source

Production puppy updates use `puppyProfiles/{dogId}/updates`, `puppyProfiles/{dogId}/media`, and `puppyFollowers/{uid}/dogs/{dogId}`. Update entries contain `authorUid`, `sourceDogId`, audience and media references. A grouped update can reference media originating on another dog. Current inventory account queries contain none of puppyProfiles/puppyFollowers; current plan KNOWN contains neither those names nor buyerContacts. The plan also intentionally holds paths with depth other than two as unclassified. Merely adding collection names would not cover descendants, cross-dog shared media, authorship or preservation when ownership changes.

Required bounded synthetic cases: deleting a former owner while preserving the current owner's dog/public or buyer-visible inherited story; keeping another author's media referenced by surviving grouped stories; deleting private former-owner content under the agreed disposition; removing a deleted follower's relation without deleting the followed dog's profile; preserving finance records but treating owned buyer contact data explicitly; restored descendant records remain quarantined until exact ledger and content/version evidence reconcile. Unknown/unclassified collections and paths must continue to hold until these cases have actual inventory, plan and replay proof.

* `vercel.json` has only the showcase-media cleanup cron. Renewal queue selection and per-task executors are guarded QA components; there is no Production deletion/renewal scheduler to activate by changing a flag.
* `withAccountMutationFence` is a prototype wrapper. Its anonymous POST path enumerates up to 201 users, and its generic query/body resolver is not verified per-route authority. It must not become a live global scan or run before webhook signature verification.
* `upload-document.js` verifies token without revocation argument, reads dog ownership, sends file.save, then independently adds document metadata. It does not call the emulator document ingress/Storage adapters. Existing request completion/finally closure cannot prove all external IO has terminated. The new ingress and Storage components reject real cloud runtime by design; retain those guards.
* `stripe-webhook.js` verifies signature inside its handler and then invokes subscription processing plus verified extra-litter post-processing. A resolver/fence belongs after verified event binding and before both effects, using pinned server customer/subscription/UID ownership proof. Wrapping the entire request before signature verification supplies neither bound actor nor per-account semantics.
* transfer-dog and claim-transferred-dogs use transactions, but a pre-handler ownership read is insufficient. The source and destination account locks and pinned dog version/owner must be checked in the same ownership-changing transaction; preserve original breeder tenantId and existing privacy snapshots. Claimed email candidates must remain bounded and rechecked, not used as authority by themselves.
* Processor calls provider.confirm after actual Auth removal and requires matching confirmation mode before completion. Existing synthetic/QA ledger confirmation is not a durable operational no-send outbox. Add a completion-bound outbox protocol with pre-removal recipient binding, idempotency, crash recovery and independent receipt validation; do not send messages in approved QA scope.
