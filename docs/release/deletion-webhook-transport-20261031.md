# Private loopback Stripe SDK transport — 31 October 2026

Prior webhook proof counted invocations of an injected cancellation callback, not HTTP attempts. The SDK default retry policy could not be inferred from that count. This increment tests real SDK transport to an explicit loopback fixture, without using actual Stripe credentials or provider resources.

createEmulatorLoopbackStripeTransport is disabled by default and requires the existing actual demo/Auth/Firestore/Storage guard. It copies a bounded synthetic UID/UUIDnonce/customer/subscription scope. Customer/subscription IDs must have explicit synthetic prefixes. Origin must be exactly a literal127.0.0.1 HTTP origin with an explicit nonprivileged port, no userinfo/path/query/fragment. No credential parameter is accepted: the private SDK instance receives only a nonce-bound, clearly synthetic loopback token generated internally. There is no Stripe network mode or client instance exposed to callers.

Private settings are pinned to that host/port/protocol, five-second timeout and maxNetworkRetries0. A custom Node HTTP client checks settings, endpoint, exact subscription path, method, expected fake authorization context and absent account/context overrides before every socket request. GET expansion fields are allowlisted. DELETE requires a current execution guard outside the SDK and again at physical transport entry. Cancellation parameters are copied and allowlisted. Response subscription ID, livemodefalse, customer, UID and nonce must all match. An unrelated test SDK client retains its own retry setting.

The existing prepared webhook scope exposes a read-only execution recheck so the transport can verify the source lock/customer/lease immediately before a DELETE. It does not expose closure or release authority. The actual prototype route now refuses to borrow its ordinary Stripe client: provider reads/cancellation hold with WEBHOOK_PRIVATE_TEST_TRANSPORT_REQUIRED until a separately bound approved provider transport exists. Ordinary deployment behavior is unchanged. This explicitly prevents the new prototype from silently using an unpinned real SDK client; the loopback fixture is never wired as a real provider endpoint.

Eight actual SDK/emulator/loopback cases are prepared. They cover origin/scope rejection before IO and copied allowlist; successful two binding GETs plus one actual DELETE with response_observed and parent lease stillactive; retry-advised500 and dropped response after a possible applied cancellation with exactly one observed DELETE, immutable sending intent and no second DELETE after restart; lock during the second binding read with zero DELETE; and livemode/customer/nonce response mismatches before cancellation. Fixture teardown closes only its own loopback server/sockets. Application leases/intents are never force-closed by teardown or elapsed time.

This establishes neither a provider-issued webhook nor actual Stripe TEST-account/key binding, independent provider readback or global in-flight drain. The local server's canceled status and response are not terminal authority.
