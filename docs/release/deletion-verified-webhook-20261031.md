# Signature-first scoped webhook prototype — 31 October 2026

The generic prototype ingress wrapper previously enumerated users before the Stripe route verified the event signature. It also could not bind the subscription core and Extra Litter post-processing to one verified account/customer scope or recheck that binding in every effect transaction. This increment moves the prototype route's scope resolution after signature verification; ordinary deployments retain the existing path.

prepareEmulatorVerifiedStripeEvent is disabled by default and requires the existing actual demo/Auth/Firestore/Storage runtime guard. Raw bytes are copied and verified before any account read or provider call. Test-mode event ID/type/customer and a synthetic UID are required. UID comes from verified metadata or, for invoices, the exact customer-bound subscription; server users/{uid}.stripeCustomerId must already match. Missing, ambiguous or changed bindings hold, not adopt/reconstruct identity. No global users query or fallback owner is used. This does not prove global customer uniqueness or restore-generation admission.

A deterministic per-account/event durable lease pins the immutable event hash/customer hash. The guarded Firestore facade checks current customer, account deletion lock and exact active lease in the same transaction before the core event claim, each entitlement transaction, completion/failure marker and Extra Litter credit. Direct foreign-user references and global users queries are refused. Provider subscription reads validate exact subscription/UID/customer, and cancellation rechecks immediately before sending. Existing price, SMS, event idempotency/order, breeder identity and paid Extra Litter rules remain owned by their original handlers.

Cancellation persists an immutable per-subscription request intent before one invocation of the injected cancellation function. Unknown/lost response keeps sending state across restart; any existing intent prevents another send, including changed parameters. Callback count is not proof of one HTTP attempt: Stripe client transport mode/retries and actual provider-issued request/readback are not established by these emulator cases and remain required before real provider activation. A returned response may be recorded as response_observed, but does not certify independent provider readback/drain. No callback, success response, error, expiry or elapsed time releases the parent mutation lease. Even a 200 webhook leaves the original lease active until a separately proved terminal/drain protocol exists. This conservative hold is deliberate and is not operational readiness.

The actual route passes guarded dependencies to the existing subscription core and Extra Litter post-processor only in prototype-emulator mode. Invalid signatures still receive the canonical core400 before account IO; the outer generic wrapper no longer scans users for this route. No Production activation, provider setting or SDK/API-version migration is included.

Ten additional actual emulator cases are prepared: invalid-signature zero-IO ordering; server customer mismatch before lease; successful subscription entitlement with one reused hold and foreign/global query rejection; invoice exact-subscription UID resolution; late lock before core claim; late lock between core and credit; unknown cancellation with one send across restart; foreign subscription before cancellation; real Extra Litter credit/idempotency; changed customer blocking later transactions/provider reads. Existing Stripe SDK crypto verifies locally signed fixture payloads with ephemeral in-memory random material, no API key, Stripe network call or message. This is not proof of a provider-issued webhook signature or actual cancellation. Runtime price/SMS semantics remain covered by original contracts.
