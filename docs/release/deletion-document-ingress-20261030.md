## Durable metadata-session recovery candidate — 30 October
The emulator-only adapter now stores schema2 immutable Auth evidence and can resume an exact UUID lease with a fresh valid token from the same account identity. Resume never creates a replacement lease, changes an epoch, adopts a current profile as historical evidence or automatically closes an abandoned hold. Old schema1/Auth-unbound leases stay held. Resumed active writes still check the current deletion lock, exact dog version/content and persisted lease binding transactionally; closed receipts still validate the exact record/input/content on retry.
Identity verification checks revocation/disabled status, UID, creation evidence, normalized email, phone, tenant and provider bindings. Only a private SHA256 fingerprint/evidence type is persisted, not an email, token or raw Auth account response. The SDK rounds UserMetadata.creationTime to a UTC string with second precision (confirmed in the installed firebase-admin source). An initial test exposed a real same-second SDK timestamp collision; merely waiting before recreation would hide the problem. The fix obtains precise createdAt milliseconds via the end-user accounts:lookup endpoint against the already-validated loopback emulator only, with a restricted response field mask, no redirects and a bounded timeout, then cross-checks UID/email/phone/tenant and SDK whole-second consistency. No admin account export, password-field request, cloud API credential or provider configuration is used. Missing, malformed, mismatched or unavailable evidence fails before lease creation.
References: https://firebase.google.com/docs/reference/rest/auth (end-user getAccountInfo) and https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/UserInfo (createdAt milliseconds). These are evidence semantics, not an authorization to add a live endpoint.
